# Prism核心面试问题

## 11. 核心面试问答：优先掌握这 12 题

沿简历的主要工作准备：先讲架构和个人工作，再讲检索、决策、MCP、Skills、缓存与恢复，最后解释效果依据。细节反例并入相关回答，不单独扩成题库。每题先口述第一段，继续追问时再展开后面的机制。

### Q1：介绍一下项目架构，一次请求怎样走完，你主要负责什么？

Prism 是研究与交互式决策工作台，前端使用原生 JavaScript 和 SVG，后端由 Node.js 提供 HTTP 服务，LangGraph 组织研究流程。用户需求先形成比较契约，再检索、读页、提取和审查事实，之后由程序计算资格和排序，模型解释取舍，用户通过 What-if 调整条件并保存判断。

我主要做研究角色与交接、资料证据约束、分支计算、交互和可靠性集成。决策版本保存为 JSON，研究阶段状态由 SQLite Checkpoint 保存，Redis 只缓存短期搜索结果；模型、图框架与搜索组件是采用的开源基础，不能都称为自研。

### Q2：为什么拆成四类 Agent？与单 Agent 或固定工作流相比有什么价值？

四类角色分别负责协调、研究、审查和分析，通过独立任务对象、上下文投影和工具白名单隔离职责。研究角色可以访问外部资料，审查角色只能检查已有证据，分析角色不能改写事实与资格；它们共用模型服务、顺序执行，不是四个模型或四个进程。

整体属于受控工作流，模型在角色范围内规划查询和补查方向。拆分便于约束权限、定位问题和维护阶段状态，但增加调用与交接开销。目前没有固定预算的单 Agent 对照，不能直接宣称多 Agent 更准确；若做比较，需要固定模型、任务、来源与预算，再看成功率、事实支持、成本和延迟。

### Q3：LangChain 与 LangGraph 有什么区别，为什么在这个项目中选 LangGraph？

LangChain 提供模型、工具和 Agent 等抽象与集成；LangGraph 更侧重显式状态、节点、控制流与持久化。Prism 用 LangGraph 组织父图和角色子图，用 LangChain 生态的 ChatOllama 适配模型，HTTP 后端则是 Node.js，所以两者不是二选一，也都不是 HTTP 服务框架。

普通 async 函数可以完成顺序研究，但加入阶段恢复、结构化交接和审查补查后，图更便于统一状态与执行边界。框架不会自动赋予自主性或事实正确性；我的选型依据是状态管理和恢复需求，不是认为图比函数天然先进。

### Q4：资料检索具体怎么做，BM25 由谁实现，怎样防止“有引用但引用错”？

接入 tofu-search 多引擎检索及其内部 BM25 重排，再读取实际目录与详情页面。BM25 是依赖内的 Python 实现，不是应用自建 FTS5 或使用 rank_bm25。它通过词频饱和与文档长度归一化衡量词法相关性，不能判断参数是否属于同一配置。

因此后面还要建立字段、候选配置、来源 ID 与原文之间的引用关系，检查类型、单位、实体及报价条件。页面出现价格不代表它是当前配置的无条件标价；争议字段暂缓采用，缺证保留未知。独立审查提出的问题也必须附原文依据，不能生成替代数字。

### Q5：模型如何辅助决策？What-if 计算和模型分析分别负责什么？

模型负责选择比较维度、组织资料和解释方案取舍；程序负责硬条件、评分和排序，用户确认最终选择。高分不能抵消超预算，缺少关键数据也不能按平均值补齐后视为通过。模型解释必须建立在已有引用与程序结果上。

目前分析阶段保存简短总结和最多两条绑定候选、字段、来源的 insight，还没有完整的独立决策报告。What-if 复用已有事实重新计算条件，不生成新资料；新增字段或补充候选仍需要研究。不能把所有对话都描述成无需模型或搜索。

### Q6：What-if 的条件继承和评分怎么实现？为什么需要显式覆盖标记？

分支保存父关系、条件、权重、候选范围及覆盖标记。父条件变化时，未覆盖字段继续继承，明确改过的字段保持自身设置；即使父子值暂时相等，也不能丢失“用户明确覆盖”的语义。这样才能在后续修改、保存与导入后保持一致。

各分支先过滤硬条件并区分缺证，再做归一化加权评分。未指定固定范围时，归一化依赖传入候选集合，新增极端候选可能改变排序，所以分数是相对效用，历史判断需保留当时事实和范围。基于已有候选数据，通过前后端共享计算内核完成条件重算，无需再次调用模型或搜索。

### Q7：Redis 放在什么位置，主要解决什么问题？并发未命中和故障怎么处理？

Redis 位于搜索 provider 层，以查询、提供方、选项和作用域等组成键，采用 Read-through 与 TTL 复用重复搜索结果。启用缓存路径时，进程内 Map 保存同键 Promise，让并发请求等待同一次加载，完成或失败后清理；关闭缓存时不经过这层合并，跨进程也不能共享 Map。

缓存操作有超时与冷却，失败时降级真实搜索，搜索本身失败继续传播。结果保留原采集时间，TTL 不能保证价格仍有效。它不保存最终模型答案、业务版本或任务队列，也没有实现分布式锁。

### Q8：MCP 怎么封装的，是你自己写的吗？为什么不直接调用函数？

协议复用官方 TypeScript SDK，我实现工具注册、参数 Schema、业务函数映射和结构化结果适配。应用 Client 实际执行初始化、tools/list 和 tools/call，再由 Server 调用搜索、目录、详情及原图读取能力。默认使用 SDK 内存传输，也提供外部 stdio 入口。

协议化便于统一和复用接口，但会增加序列化与依赖开销，不代表提高准确率或速度。角色能用什么仍由应用白名单决定，read-only 标注不是授权；协议成功也不等于网页事实正确，证据规则继续检查业务结果。

### Q9：Skills 与普通提示词有什么区别，什么时候加载，怎么限制权限？

Skills 把任务指导做成独立、可版本化的 SKILL.md 包。当前有规划、商品研究、租房研究、证据审查、决策分析五个技能；先发现名称、描述和指纹，再按角色与明确任务关键词加载选中正文，注入模型上下文并记录实际版本。当前选择逻辑由代码实现，不是模型自主路由。

加载器校验受信目录、名称、大小、符号链接及发现后内容变化。技能只能指导方法，不能新增工具权限或跳过业务校验。现有测试证明加载与隔离正确，没有做 Skills 效果提升对照；不能把文件格式正确说成研究准确率更高。

### Q10：Agent 怎样控制执行边界？遇到证据不足或审查失败怎么办？

通过结构化输出、角色上下文与工具白名单控制范围，研究最多一个恢复阶段、两次模型审查。有效审查反馈会暂缓对应事实并进入定向补查；来源和观察未变化时不重复审查，避免反复询问直到模型给出通过。

资料仍不够就保留缺证或无可比方案，不能擅自放宽预算。审查不可用时明确记录降级，结果仍受程序证据规则约束，但不能声称已经通过独立模型审查。提示词表达规则，真正的动作范围、次数和资格由代码执行。

### Q11：SQLite Checkpoint 能恢复到哪一步？能保证外部调用只执行一次吗？

父图使用任务 ID 作为 thread_id，将阶段状态和产物保存到 SQLite；子图没有各自独立的持久化器。恢复时可以跳过已完成并落盘的父阶段，不是从任意函数语句或最后一个 token 继续，也不等同于保存整段聊天。

如果搜索已经完成但阶段检查点尚未提交就崩溃，恢复后可能再次搜索。Checkpoint 不自动提供外部副作用的 exactly-once 语义，版本提交等写入需要单独考虑幂等。面试时应说明真实恢复边界和重复调用窗口。

### Q12：你怎样验证项目收益？简历上的三个数分别说明什么？

35/35 是构造的证据规则回归，不是真实抽取准确率。P95 0.66ms 是历史指定环境下，九个合成候选、七情景、一千次变更的计算内核结果，排除了模型、网络和页面绘制。缓存 9→3、减少 66.7%，来自三组查询各重复三次的受控对照，不是线上延迟或研究质量提升。

307 项单元／HTTP 和 71 项 Edge 测试验证软件与交互行为，同样不能换算为 Agent 成功率。完整效果应固定任务、模型、来源和预算，统计候选覆盖、字段支持、失败、耗时与成本；用于修复系统的任务不能再包装成独立测试集。
